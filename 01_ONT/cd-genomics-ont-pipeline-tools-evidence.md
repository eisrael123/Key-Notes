# CD Genomics ONT Pipeline: Tools, Evidence, Outputs, and Biological Significance

Reconstruction of the CD Genomics Nanopore Direct RNA-seq pipeline (order `CGEKDRSacRIP2634`, EBV Zta reactivation: `SVP_Ctrl_1-3` vs `ZTA_Test_1-3`), built by cross-referencing their PDF report (`CGEKDRSacRIP2634  report by Nanopore Direct RNA-seq.pdf`) against direct inspection of the delivered `CGEKDRSacRIP2634/` directory tree, plus manual BAM/FASTQ header inspection (`samtools view -H`, `zcat | head`). No pipeline code (Snakemake/Nextflow/scripts) was delivered — everything below is inferred from the report text, the Software List (Table 21, report p.76), file-path citations embedded in the report, and my own directory/header inspection.

## Reference files used (not in the software table, but load-bearing)

Report §2.3.1/2.3.2 (p.11, filenames highlighted in the original PDF): **GENCODE GRCh38 (`gencode.v49.transcripts.fa`) + `EBV_Akata_inverted.transcripts.fa`** for transcriptome alignment, and **`GRCh38.p14.genome.fa` + `chrEBV_Akata_inverted_2.fa`** for genome alignment. This is a *different* reference bundle than the lab's own `/Applications/ngs/pipelines/docker-rnaseq/referenceFiles/hg38plusAkataInverted/` (which uses Ensembl GTF release 113, not GENCODE v49) — CD Genomics sourced their own reference rather than reusing the lab's, so annotation versions won't line up exactly if this ONT data is ever compared coordinate-for-coordinate against short-read results from the lab's own pipeline. The `_2` suffix on the EBV genome filename also suggests a revised/patched version not identical to the lab's own EBV FASTA.

## Incidental finding

The minimap2 `@PG` command line preserved in the BAM headers leaks CD Genomics' internal server path: `/nfs_backup/lukeying/RNA/DRS/05_CGEKDRSacRIP2634/`, run inside a conda environment named `flair_env2`. The `flair_env2` name suggests they may have originally scaffolded this analysis around **FLAIR** (a different long-read isoform-calling tool) before settling on Bambu for the final delivery — a glimpse of internal iteration, not something that affects interpretation of the results.

## What's genuinely missing (not recoverable from any delivered file)

Checked directly: FASTQ read headers (`@<uuid> <mean_qscore>`) carry no basecalling-model info, and the BAM headers preserve minimap2's and samtools' `@PG` lines but **not Dorado's** — so the exact Dorado basecalling + modification-calling model versions used are not recoverable from anything delivered, only the software version number ("v2.0.0", itself inconsistent with the "v1.0.2" given for the polyA step). Raw POD5 signal (4.2TB, `00.rawdata/pod5/`) is fully present, so the pipeline could be rerun from scratch with current best-practice models — it just wouldn't be bit-identical to CD Genomics' original run, which doesn't matter for a differential biology question (see [[rnaseq-pipeline-walkthrough-and-tx2gene-mapping]] for the general reproducibility framing).
